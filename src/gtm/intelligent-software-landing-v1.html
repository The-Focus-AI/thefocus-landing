Not another fixed application

A runtime for bounded habitats.

Each habitat can carry its own code, tools, model, data, credentials, sessions, and interface. Gaia makes those environments operable and composable—not merely generated and handed off.

The changed lifecycle

From request to revised artifact.

Software can remain visible and editable while it runs. A declaration becomes an environment; use creates evidence for the next revision.

Safety is architecture

Useful freedom needs hard edges.

A dynamic system should make authority, execution, and change easier to inspect—not hide them behind a chat box.

01

Separate containers

Habitats execute in isolated runtimes rather than sharing one undifferentiated process.

02

Scoped credentials

Each environment receives the access intended for its bounded job.

03

Persistent state

Workspace state survives runtime changes instead of disappearing with a generated response.

04

Iframe boundary

Foreign components render across an iframe boundary, separating generated surfaces from the host.

05

Visible artifacts

Executable code and declarations remain human-visible and available for review.

06

Reconciled operation

Fleet start and stop are explicit desired states, checked against observed state.

What we will not pretend

Working runtime. Evolving practice.

Credibility comes from naming the current boundary as clearly as the direction.

Generated changes still need verification.

Human-visible artifacts and runtime boundaries support review; they do not make generated code automatically correct.

Live-model authoring is manually tested.

The dynamic lifecycle works, but its live-model authoring path is not presented as comprehensively automated validation.

Gaia is not a universal no-code app generator.

It is a working, evolving runtime for purpose-built habitats with bounded capabilities.

Evaluation is adjacent, not an automatic gate.

Evaluation exists in Umwelten, but it does not automatically gate every Gaia-generated component today.
